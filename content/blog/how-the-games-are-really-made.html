The short version

Every game on this site is a real ZX Spectrum program: Z80 machine code, assembled into a tape image that loads through the Spectrum’s own ROM, as a tape did in 1987. Almost all of that code, the graphics, the music and the documents around them were produced by AI coding agents (Claude Code; the tools also support OpenAI’s Codex) working in ordinary Git repositories. One person, me, sets the direction, answers questions and decides what ships.

That would be a recipe for convincing-looking junk without one rule the whole process is built around: no agent is trusted to say its own work is good. Every stage ends in something a machine can check (a linter, an assembler, a simulator run, a hash) or a review by a different agent that starts with no memory of the work. The rest of this post is about how that is put together.

  1. Specification. An idea is questioned until it is a machine-agnostic game spec, then linted.
  2. Design. The spec becomes numbered requirements, a memory and timing budget, and milestones.
  3. Assets. Sprites, screens, music and sound are made, converted to Spectrum formats and reviewed.
  4. Build. Z80 source is written and assembled with sjasmplus into a hashed tape.
  5. Verify. The tape is cold-loaded and played by scripts in a Z80 simulator; timing, input latency and flicker are measured.
  6. Playtest. An agent plays the tape in a browser emulator and files findings by severity.
  7. Gate. A fresh agent checks that every piece of evidence is about the same tape and gives a verdict.
  8. Media kit and publishing. An evidence-bound magazine review, the cassette inlay, and the demo on this site.

Research before code

An agent asked to “write a Spectrum game” writes the kind of Spectrum game that appears in old type-in listings: flickering sprites, a main loop with no idea of time, keys that are missed. So before any game, the toolkit (spectrum-game-reference, a private repository) studied how the best commercial games actually worked.

  • The corpus. 83 games were loaded, run and disassembled: 72 well-rated exemplars chosen from ZXDB scores and awards, and 11 badly reviewed ones kept as examples of what not to do. Cheaper static metrics cover another 2,635 TOSEC titles.
  • The stages. Each game is fetched and fingerprinted, converted to a snapshot with SkoolKit’s tap2sna, traced in SkoolKit’s simulator (a T-state profile, every AY sound-chip register write, memory paging and a model of the TV beam to spot tearing), then disassembled with sna2skool from the traced state.
  • Pattern cards. Techniques that recur across games become short Markdown cards with measured costs: bytes, T-states (Z80 clock cycles) and frames per update. There are about sixty, from memory budgets to multi-voice beeper music.

A pattern card is the kind of thing an agent can follow and a reviewer can check. This is the top of the beeper-music card, abridged:

| Game        | Voices | How voices are mixed  | Loop cost                   |
|-------------|--------|-----------------------|-----------------------------|
| Agent X II  | 5      | pulse interleaving    | 76 T per bare loop (46 kHz) |
| DreamWalker | 3 + noise drums | phase accumulators | about 153 T per loop  |
| Cobra       | 2 + percussion | periods N and N-1, XOR-mixed | ~18 toggles per frame |

Skills, plugins and agents

The working knowledge lives in skills. A skill is a folder with a SKILL.md (when to use it and the steps to follow), reference documents, templates and scripts. Claude Code and Codex load a skill’s instructions when a task matches its description, so an agent asked to build a frame loop gets the measured frame-loop contract, a reference routine and a validator, not a guess.

The skills are grouped into five plugins, versioned separately (versions as of this post):

PluginSkillsWhat it is for
game-spec 0.1.06From idea to a checked, machine-agnostic specification
zx-engine 0.6.86Frame loop, flicker-free sprites, beeper sound, 8-way steering, waggle input, dictionary lookup
zx-assets 0.23.414Manifest, art direction, sprites, animation, screens, isometric and 3D models, AY music and effects, speech, text, review
zx-game 0.20.05Design, build, verify and playtest, one milestone at a time
zx-media-kit 0.16.06Magazine review, inlay, adverts, video, website publishing

Some steps are given to agents rather than skills: separately defined sub-agents that start in a fresh context with only the files they are pointed at. The playtester, the milestone reviewer, the asset judge, the asset reviewer and the magazine reviewer are agents for the same reason: someone who did not do the work is the only one who can be trusted to check it.

The toolkit is its own plugin marketplace while plugins are developed. A copy without tests or virtual environments is published to a release marketplace (zx-plugins), and a game template repository pins a tagged release, so a new game starts from a fixed set of skills rather than whatever is on the working branch.

Stage 1: the specification

A game starts as a sentence. The game-spec-grill skill questions it in numbered rounds, each question with a recommended answer, until every branch is settled: pillars, actions, world, hazards, progression, scoring, failure, tone and scope. Answers go into a decision log. game-spec-write then writes the specification in a fixed template, with numbered rules, a tuning table and Given/When/Then acceptance checks.

The specification is deliberately machine-agnostic. It may not mention pixels, frames as a unit of time, bytes, sound chips or key bindings, because those are decisions for the target machine. check_spec.py enforces it:

  • platform leaks are errors (machine and device names are warnings);
  • required sections must exist;
  • requirement, tuning and acceptance IDs must be well formed and unique;
  • no TBD or TODO may remain;
  • music must have a way to be switched off.

Only at game-spec-implement is a machine chosen. It writes a separate target brief (for example Gold Master, target ZX Spectrum 128) with controls, display, sound and memory, and leaves the specification untouched. The specification for Gold Master is at version 1.1.1: one tuning revision after the fourth milestone’s playtest, and one name change. Changes are meant to go through game-spec-revise, which separates “the code is wrong” from “the rule is wrong” before anything is edited.

Stage 2: design, budgets and milestones

zx-game-design turns the specification into three documents: requirements.md (numbered R-001… requirements, each citing a section of the specification), design.md (memory and bank map, controls, which engine skills and pattern cards to use, and a T-state budget for every subsystem) and milestones.md (playable slices, each with acceptance checks that a script can run).

The design is turned into a build.yaml that the build and the verifier both read. An extract from Gold Master’s (abridged, comments shortened):

machine: 128
main: src/main.asm
clear: 24575            # just below the resident data
banks:
  0: bank0.bin          # sound player + tune, ticked by the ISR
  1: bank1.bin          # Production (+ its level-2 staircase) and landing 1 pictures
  7: bank7.bin          # Percy and the M3 items above the play scratch
update_frames: 2        # frames per game update (IM2 counter)
update_budget_t: 125000 # busy T per play update, p90
latency: {key: p, watch: HARNESS_player_x}

That last line matters later: it tells the verifier which key to tap and which variable in memory must move when it does.

Stage 3: assets

The zx-assets pipeline starts from a manifest derived from the specification: every sprite, tile set, screen, music cue and effect, with its size, frame count, colours, memory budget and a reference back to the specification. Then, in order: art direction, sprites, animation scripts, screens and tiles, AY music, sound effects, speech, text, and an independent review.

  • Art. Character references and scene paintings are generated with Google’s Gemini image model, under a hard cap of 10 images per character and per scene, counted in a sidecar file before every call. At the art-direction gate I pick the master reference from up to three candidates, or in an unattended run the zx-asset-judge agent does, and can veto any that breaks the specification’s tone rules.
  • Reduction. The picture is then reduced to what a Spectrum can show: one ink and one paper colour per 8×8 cell, with a strategy for colour clash. Sprites are stored as plain-text art that an agent can read and edit, and converted to assembler data, masks, shifted copies and mirror images by scripts. At sprite sizes a figure is often better designed than reduced, so many sprites are drawn directly as text art. The top of a 24×32 sprite drawn that way:
@sprite brian nomirror
........########........
......############......
.....##############.....
.....###o#o#o#o#o##.....
....##oooooooooooo##....
  • Music. Tunes are composed as MIDI and reduced to the 128K’s three AY-3-8912 channels at 50 updates a second. A Z80 interrupt player is built and run in the simulator, and its register writes are checked against the arrangement. Sound effects share the chip on channel C, by priority.
  • Review. At the last gate a fresh zx-asset-reviewer agent runs the validators, builds a gallery tape, looks at simulator screenshots and gives a pass, pass-with-issues or fail verdict, with at most two fix rounds.

Not everything comes from an image model. Many of Gold Master’s rooms and sprites were drawn directly in Python scripts that an agent wrote, with the cast sheets used only to keep people recognisable.

Stage 4: building the tape

The code is Z80 assembly, assembled with sjasmplus 1.24.0 (built from source, and in the template’s dev container). zx-game-build starts from a template game, takes the engine from the validated zx-engine skills and pattern cards, wires in the asset data and measures each subsystem against its budget.

build_game.py reads build.yaml, assembles with -DMACHINE=48 or 128, writes the loader, loading screen, main block and memory banks to a tape image, and records the tape’s sha256 in build-m<N>.json. That hash is the identity of a build for every later stage.

Every game also exports a small set of harness symbols: labels the test tools look up in the assembler’s symbol table to read the game’s state from memory, without the game knowing it is being tested:

HARNESS_updates     equ updates
HARNESS_state       equ state
HARNESS_lives       equ lives
HARNESS_score       equ score
HARNESS_level       equ level
HARNESS_player_x    equ mo_x
HARNESS_player_y    equ mo_y

Gold Master is 55 source files: 19 hand-written (about 7,500 lines of Z80) and 36 generated or shared house code, 11,400 lines in all. Wordris is about 3,400 hand-written lines.

Stage 5: verification in a simulator

verify_game.py is the largest script in the plugins (about 2,700 lines). It runs the tape in SkoolKit’s CMIOSimulator with memory and I/O contention modelled, so timing is close to a real 48K or 128K, and runs these checks, among others, in order:

  1. build and memmap: the tape assembles and fits.
  2. cold_load: the tape loads through the real ROM, as from a cassette.
  3. reaches_play: the game gets from the title to play.
  4. update_rate: the game keeps to its declared rate, on average and in its worst 100-frame stretch.
  5. update_cost: busy T-states per update, from the update tick to the next HALT, interrupt included; fails if the 90th percentile is over budget.
  6. no_crash and no_soft_lock.
  7. input_latency: 30 one-frame key taps at irregular moments; every one must move the watched variable within one update, and an idle run without the taps must not move in the same windows.
  8. flicker: a beam model counts screen bytes that were erased and redrawn while the beam was passing them. The pass mark is zero.
  9. One check per bot recipe, then music and sound toggles, audio, house style, sprite contact and game-flow checks.

Here are three real rows from Gold Master’s fourth-milestone report:

| update_cost | PASS | 92986 play updates over 45 run(s): median 77839, p90 97075, max 196438 busy T
  (max in recipe-m3-ship4 frame 6473); p90 is 68% of the update period (2 x 70908 T);
  update_budget_t 125000: p90 within budget |
| input_latency | PASS | 30/30 one-frame taps raised player_x within 3 frames (tap frame +
  update_frames 2); slowest response at tap+1; idle drift 0 ... |
| flicker | SKIP | not measured: the displayed screen flips during play ...; the beam model does
  not follow shadow-screen double buffering |

Note the skip. Gold Master draws into the 128K’s second screen and flips between them, and the beam model cannot follow that, so the report says so instead of passing it. Wordris, which draws to one screen, reports “0 transient bitmap bytes in 516 play frames”.

Recipes are the game’s functional tests: a key log plus expectations, in JSON. This one presses Space to start, runs the courier clock down with one poke, and expects the game to go from play to the missed-courier card, to the title and back to play, with no score:

{"keys": "150-154:SPACE", "frames": 1600,
 "pokes": [{"frame": 600, "symbol": "clock", "value": 50, "size": 2}],
 "screenshots": [700],
 "expect": {"state_sequence": [1, 3, 0, 1], "state_at_end": 1,
            "symbols": [{"symbol": "clock", "size": 2, "seen": [9000]},
                        {"symbol": "HARNESS_score", "size": 2, "max": 0}]}}

A recipe that pokes memory is labelled a fixture in every report, because it skips part of the game. Longer journeys are played by closed-loop pilot scripts that read the harness symbols each frame and decide which key to press; their key logs must then replay identically. Gold Master’s fourth milestone ran 43 recipes.

The simulator is busy work for a machine, so at most three verifies run at once, and a run that fails only because the machine was overloaded is marked INFRA and does not count against the fix budget.

Stage 6: an agent playtests

Scripts check what someone thought to write down. To find the rest, a fresh zx-game-playtester agent plays the tape. playtest_server.py serves a local page with a patched build of JSSpeccy 3.2 (the same emulator that plays the demos on this site) that exposes a window.zx object: pause, single-step, speed, key down and up, memory peeks, recipe replay and screenshots. The agent drives it through Claude in Chrome, following a written charter. When the browser tool is unavailable, it steps the tape in the simulator instead and says so in its report: Gold Master’s first eight rounds were played that way.

It plays slowly or a frame at a time, because an agent cannot react at 50 frames a second, and it reports what it saw with screenshots and a findings table graded by severity: 1 for a crash, soft lock, impossible progress, broken controls or a tone breach; 2 for unfair or unclear; 3 for polish. Severity 1 blocks the milestone; 2 and 3 are triaged. A milestone gets at most five fix attempts, counting failed verifies and failed gates as well as playtests, before it is marked stuck and handed to me. Gold Master took 12 playtest rounds across its four milestones (3, 2, 1 and 6); the third Wordris milestone took nine.

Stage 7: the gate, and the time it said no

A milestone is signed off by the zx-game-reviewer agent, which reads the requirements, the build record, the verify report and the playtest reports, and checks one thing first: that they all name the same tape sha256. A verify of one build and a playtest of another prove nothing about either. It then checks each acceptance criterion against evidence and appends a verdict: pass, pass with issues or fail. It treats a skipped check as no evidence, requires recipes that poke memory to be labelled as fixtures, and looks for anti-goals, including claims of tests that did not happen.

It does fail things. Gold Master’s second milestone passed 53 of 56 verify checks and its playtest had no severity-1 findings, but the gate compared each screenshot the playtest cited with the room the playtest’s own log said it was in:

Verdict: fail
- blocking: cited room screenshots show a different room, and Accounts has no rendered
  evidence. ... Each was taken within the room change's hold of the old picture (F-15).
- what must change (no source change and no rebuild needed; a new playtest round on the
  same tap 34413f9b): capture landing 2, Commissioning and Accounts at least about 20
  frames after `room` changes ...

The game was fine. The evidence was not: screenshots taken a moment too early showed the previous room, so the report’s claims about a room nobody had actually looked at were unsupported. A second playtest round on the same tape fixed the evidence, and the milestone passed with issues. That is the behaviour we want from a reviewer, and the reason the reviewer is never the agent that did the work.

Each verdict also says plainly what was not verified. From Gold Master’s final gate:

Not verified: feel at full speed (all of rounds 3-6 were stepped); real hardware and a real
Kempston interface; ... sound by ear (AY register data only)

Stage 8: the magazine, the box and this website

The INK & PAPER reviews quoted on each game page are written by zx-magazine-reviewer agents in a mid-1980s magazine voice, but they are not free fiction. Every claim in a review carries hidden evidence IDs pointing at a verify check (V-), a playtest finding (P-), a screenshot (S-), a requirement (R-) or my own play reports and verdicts (O-), and check_review.py rejects a review with an unsupported claim. Three reviewers write independently; the kit takes the median scores and the text of the reviewer closest to them. An open severity-1 finding caps the Overall score at 59%.

The same kit renders the cassette inlay, an advert and a poster from real emulator screenshots, a gameplay video and a video of the real tape loading.

The last step is this site. publish_site.py, from the zx-website skill, writes a game’s folder here from its media kit. It refuses a kit that is out of date against the release tape and never publishes the release tape: the demo is stored obfuscated, and the site’s tests require every demo to be a separate single-level demo build. The site itself is built by a single Python standard-library script and checked by tests in CI before GitHub Pages deploys it: every demo must decode to the hash recorded for it, hidden games must not be deployed at all, internal links must resolve, images must declare their sizes, and no price may appear on a game page.

Linters, hooks and CI

Agents write a great deal of text quickly, so the cheap checks run on every commit. Every game repository carries the template’s pre-commit hooks:

  • Gitleaks on staged changes, so no API key reaches Git;
  • markdownlint for the many Markdown documents, and typos for spelling;
  • ruff for Python and shellcheck for shell scripts;
  • basic file checks: merge-conflict markers, valid JSON, TOML and YAML, line endings and large files;
  • three local hooks: check_spec.py --strict on the specification, the asset manifest validator, and a check of the game’s identity file.

The games have no hosted CI: the verifier needs the toolkit, takes minutes per run and is the real test, so it runs locally and its reports are committed with the build. The toolkit’s plugins have their own unit tests (over a hundred test files). The Dalex Studio repository has the heaviest CI, because it is a C++ engine: pre-commit, clang-format and clang-tidy on changed lines, basedpyright on its Python (failing only on new findings), pip-audit, unit tests with coverage, and a native build against a pinned ScummVM commit.

Decisions are written down rather than left in chat history: each game has a decisions log, each repository records larger choices as numbered decisions or architecture decision records, and work is tracked as GitHub issues with a readiness policy, so that several agents can pick up work without colliding.

Watching the agents: the Studio

The office you see in the Studio film is a real program. Dalex Studio is an adventure-game engine written for ScummVM, in C++, at 640×480 with indexed-colour pixel art. Each room is a part of the pipeline and each desk a role.

It knows what the agents are doing by reading the transcripts Claude Code and Codex save on disk. A collector looks at sessions active in the last ten minutes, maps each skill or agent in use to a character, and shows that character working. It shows only the session title and the short description of the most recent tool call; command text is used only to work out the character and the game, and prompts, outputs and commands are never shown. The milestone board, the monitors behind the programmers and the accountant’s ledger are filled the same way, from the game repositories, GitHub and token-usage records.

That is useful as well as fun: with several agents running overnight across six games, a room you can glance at tells you who is stuck, who is waiting for a decision, and which game is close to a gate.

Testing the skills themselves

A skill is instructions plus code, and both can be wrong. Five of the six engine skills were validated with red/green builds (direct drive is still pending): fresh agents built the same thing with and without the skill, and the results were measured. For the frame loop, one of five builds without the skill passed the latency contract (30 irregular one-frame taps under contention), and three of three with it did. That is a small sample. The validation note states its own limits: the timing comes from a contention-modelled simulator, not real hardware, and the validator tests one sprite and one input pattern.

Skill text is also reviewed with Tessl. The Studio’s rule is a lint, a quality review and a security review for every changed skill, plus scenario evaluations where a plugin has them. The toolkit’s skills have had Tessl quality reviews, and security reviews for those with scripts; they have no scenario evaluations yet.

What goes wrong

Plenty. Some examples from the records:

  • Evidence about the wrong thing. The failed gate above. Screenshots and claims that look right but describe another moment are the commonest failure of agent testing, which is why the gate cross-checks them.
  • A demo that does not match its page. When choosing demos for this site, an early Mower Mayhem milestone turned out to steer like a tank (turn left and right, speed up and down), not with the eight-way direct drive its page described. In the end no milestone tape was published: I chose single-level demo builds for every game.
  • Stale kits. Several media kits were out of date against a newer release tape. The publisher refuses them, so they were published against the kit’s own tape and the gap recorded.
  • Tool defects found by use. Each game keeps a LESSONS.md. Gold Master’s includes status files the toolkit wrote that failed the game’s own Markdown lint, a scaffolder that cut the tape name to GOLD MASTE, and a build file parser that accepts only one level of nesting. Each was recorded as a toolkit defect; the lint failure is an open toolkit issue, and the others are still worked around in the game.
  • Releases that lag. The released plugin set lags the working branch (zx-game 0.19.1 against 0.20.0, zx-media-kit 0.14.1 against 0.16.0), so a new game starts on older skills until the next release is tagged.

What is not proven

To be clear about the limits: the games are verified in the SkoolKit simulator and played in JSSpeccy. Nothing has been checked on a real Spectrum. Agent playtests are slowed down or stepped, so the feel at full speed is judged by people playing the demos, not by the pipeline. Sound is checked as AY register data against its reference, not by ear. The reviews are generated, honestly bound to evidence, but they are not the opinion of a person who bought the tape.
